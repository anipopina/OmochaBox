# おうちバラバラ

画面をタップすると黄色いショベルカーが自動で動き、バケットでおもちゃの家を叩いて崩します。three.js で描画し、cannon-es の簡易な剛体物理で破片を落とします。得点・失敗・時間制限・文字の案内はありません。

初期仕様の Phase 3 までを実装しています。建物は3種類あり、毎回違う種類と配色の建物に進みます（最初は2階建て）。長押しでの連続攻撃、全壊後の瓦礫遊び、「次のおうち」アイコンでの入れ替えに対応しています。

| 建物                 | 攻撃回数 | 崩れ方                                             |
| -------------------- | -------- | -------------------------------------------------- |
| 小さなおうち（平屋） | 2        | 屋根と手前の壁、次に残り全部                       |
| 2階建てのおうち      | 4        | 手前から奥へ。途中で前進する                       |
| ビル（4階建て）      | 5        | 4階の壁から始めて上の階から順に。最後に1階が崩れる |

## 設計上の判断

- 建物は [house-plan.ts](house-plan.ts) に、大きな部品と攻撃ごとの破壊エリア・ショベルカー位置・バケット目標をデータで定義します。切妻屋根は共通の関数で作ります。ショベルカーは、腕が届く範囲でできるだけ後ろに停めます（攻撃ごとの `rootX`）。攻撃中に前後させず、振りかぶるアームが建物から離れるようにするためです。ビルの1撃目は、上から振り下ろすと屋上を通り抜けるため、4階の正面の壁を手前から横向きに叩きます（`style: 'side'`）。実行時のメッシュ切断や構造解析はしません。立っている部品は質量0の静的物体です。cannon-es では質量を持つ静的物体が衝突計算で動く物体として扱われるため、壊れた瞬間に質量を与えて動かします。
- アームは [rig.ts](rig.ts) の2関節の逆運動学で、打撃の瞬間に歯先が目標へ一致します。振りかぶりと戻りでは、全関節を同時に動かさず、ブームを高く上げてアームを折りたたんだままの経由姿勢を通ります（`liftPose`）。同時に動かすと、折りたたんだアームが開くときに手首が建物の中を通るためです。めり込みの量は `ouchi-model` テストで上限を検査しています。目標は必ずその攻撃で壊れる部品の表面に置き、空振りに見えないようにします。前進は前方向だけで、キャタピラは建物の正面より手前で止めます。
- 物理演算は大きな部品だけに限ります。小さな破片と砂ぼこりは物理なしの演出用で、上限のあるプールで再利用します。止まった部品は休止させ、どうしても静止しない部品は一定時間で強制的に休止させます。
- 破片はショベルカー側へ飛ばしません。前側の屋根はショベルカー側へ下る斜面なので、家の内側へ落とします。ショベルカーとバケットには運動学的な物体を持たせ、瓦礫をすり抜けずに押します。バケットが瓦礫に触れるのは振り下ろしの間だけです。振りかぶりや戻りでも触れると、瓦礫をすくってショベルカーの上へ運んでしまいます。バケットが押す速さには上限があり、破片が画面外へ飛ばないようにしています。
- 物理の正確さより「わかりやすく崩れること」を優先し、次の調整をしています。
  - 2階の床は前後・左右に4分割し、打撃点の継ぎ目から V 字に折れて落ちます。1枚の重い板のままだと、平らに落ちて衝撃を受け止めたように見えるためです。床は下の壁より少し遅れて崩します。
  - 攻撃ごとに威力（`power`）を指定できます。地面に立つ1階の壁を崩す攻撃は、威力を強めています。
  - 崩れた壁には、短時間だけ外向きの速度を保つ「押し出し」を物理演算の外から加えます。上に載った床や接触摩擦があっても、確実に倒すためです。
  - 打撃の瞬間に、近くの既存の瓦礫も弾きます。部品を崩すときは、休止中の瓦礫をすべて起こします。cannon-es は休止中の物体を動かない壁として計算するため、起こさないと新しく崩れた部品が止められてしまいます。
  - cannon-es の摩擦は、荷重に関係なく接点ごとに一定の大きさで働きます。そのため、摩擦係数は現実の値より低くしています。部品の当たり判定も水平方向だけわずかに細くして、横に隣り合うブロック同士が触れないようにしています。
- 画面全体がタップの対象です。攻撃中のタップは少数だけ予約し（上限は app.ts の `MAX_QUEUE`）、それ以上は捨てます。指を押し続けると、攻撃を1回ずつ続けます。離した時点で動いている攻撃は、最後まで再生します。
- 全壊後のタップは瓦礫遊びになります。手の届く範囲で、タップしたおおよその方向にある大きな破片を選びます。そのなかでなるべく同じ破片が続かないようにして、叩いて跳ね飛ばします。同じ場所を続けてタップしても、狙う破片は変わります。ショベルカーはその場から動きません。
- 「次のおうち」は、新しい家が急に現れるのではなく、前へ進んだ先にある形で見せます。バケットを地面近くまで下ろして瓦礫の中を前進し、瓦礫は左右へ押しのけます。押しのける姿勢と砂ぼこりは、道のりの22〜40%（`PLOW_UNTIL`〜`PLOW_END`）でゆっくり解除し、その後は待機姿勢で走ります。次の建物の前に、バケットがめり込んだまま着かないようにするためです。前方に押すと次の作業場に溜まるので、物理演算の外から横向きの力も加えています。次の家は、前進を始める時点で1区画先に建てます。区画の間隔（[scenery.ts](scenery.ts) の `SITE_SPACING`）は、縦長の画面で道の先まで見えても建てた瞬間が映らない長さにしています（`ouchi-model` テストで検査）。長い道は、一定の速さで進む区間を挟んで移動します。前の作業場を通り過ぎたら、ショベルカーは瓦礫に触れなくなります。引っかかった破片を道の先まで引きずらないためです。
- カメラの構図は全建物で共通です（ビルのときも引きません）。角度・注視点・画面に収める範囲・追従の遅れなどの調整値は、[camera-rig.ts](camera-rig.ts) の `CAMERA` にまとめています。
- 道沿いの景色（[scenery.ts](scenery.ts)）は、作業場の間隔ごとに同じ配置を繰り返します。到着したら、ショベルカー・家・カメラを1区画ぶん戻し、座標が増え続けないようにしています。景色は繰り返しなので、戻しても見た目は変わりません。前の家の瓦礫は、到着の時点で物理演算から外し、縮めて消します。
- カメラ（[camera-rig.ts](camera-rig.ts)）の構図は、縦横比に応じて作業場全体が収まるように決めます。縦長の画面ではショベルカーの後ろ寄りから見て、奥行き方向に並べます。次の家へ進むときは、臨界減衰のバネ（ゲームエンジンで一般的な SmoothDamp）でショベルカーを少し遅れて追い、進行方向の少し先を映します。ショベルカーが画面の中で固定されず、動いて見えるようにするためです。
- 描画ループは、動き・物理・演出がすべて止まると停止します。ページの非表示・離脱では停止して予約を捨て、復帰しても勝手には再開しません。バックフォワードキャッシュから戻ったときは、新しい家から始めます。
- 動きを減らす設定では、カメラの揺れと砂ぼこりを省き、破片の勢いを弱めます。次の家への移動も短くし、カメラは遅れずにすぐ追従し、先を映すずらしもしません。建物が崩れる結果と、次の家に着いたことはそのまま見えます。
- 描画回数を抑えるため、建物の箱形の部品は建物ごとに1つのインスタンス化メッシュ（大きさ1の箱を部品ごとに拡大し、部品ごとに色を付ける）で描きます。窓とドア、背景の丘もインスタンス化しています。物理演算は部品ごとに行い、見た目の位置だけを書き戻します。
- 画質（[quality.ts](quality.ts)）は最高の状態から始めます。フレーム時間の移動平均が遅い状態が続くと、描画の解像度と影の解像度を段階的に下げます。行ったり来たりしないように、1回の訪問の間は下げる方向にだけ変えます。
- 開発用の URL パラメーター：`?fps` を付けるとフレームレート・画質の段階・描画回数を表示します。`?quality=max` を付けると画質を最高に固定します（検証やスクリーンショット用）。
- 影を計算する範囲は、画面に映る地面全体から求めます。縦長の画面は道の先まで映るので、範囲が広いときだけ影の解像度を上げます。
- 「次のおうち」ボタンは、最後の崩壊が終わったときに一度だけ現れ、次の家へ進むまで出たままにします。瓦礫遊びの最中に出入りして、登場の演出が繰り返されないようにするためです。
- WebGL を使えない環境では、絵文字と短い文で遊べないことを伝えます。

## 効果音

Stable Audio Openで生成した4種類の短い音を、Web Audioで操作に合わせて再生します。BGM・待機中のエンジン音・音量設定UIはありません。

- 家への打撃：バケットが当たる瞬間に、丸みのある木のおもちゃの打撃音。
- 最後の打撃：通常の打撃音と、積み木が崩れて落ち着く音を重ねます。
- 瓦礫遊び：バケットが瓦礫や地面に当たる瞬間に、軽くつついて転がす音。
- 次の家への移動：走り始めから到着まで、控えめな玩具モーターとキャタピラの音。到着時に短くフェードして止めます。

途中の崩壊音は、連続攻撃で同じ音が繰り返されるため不採用とし、通常の遊びでは鳴らしません。候補は過去の比較用に保持します。

取得とデコードはページ内で使い回し、音の準備が遅れても操作を待たせず、過去の打撃音を後から鳴らしません。再生上限・再試行間隔・音量は [sound.ts](sound.ts) に定義します。連打で無制限に重ねず、無操作で描画が休止すると音声処理も休止します。入力キャンセル・非表示・フォーカス喪失で音を停止し、復帰だけでは鳴らしません。ページ離脱で音声コンテキストを閉じます。

比較・配信には圧縮済みMP3を使い、生成原本WAVはGit管理外の `tmp/audio-originals/ouchi-barabara/` に保管します。生成条件とハッシュはリポジトリに残します。原本の保管先がなくても選定・Webビルドは行えますが、原本からの再加工には復元が必要です。

配信用MP3と原本の参照・生成条件・加工・利用条件の記録は [効果音素材](../../source-assets/ouchi-barabara/audio/README.md) を参照してください。

### 効果音の比較（試行）

「選定結果をコピー」は、書き出しと同じJSONをチャットへの貼り付け用にコピーします。コピーが許可されない環境ではJSONを表示・選択して手動コピーできます。選定変更時には古い手動コピー表示を隠します。

`npm run dev` で起動し、`/ouchi-barabara/?sound-review` を開きます。各場面で音源の記号を固定し、初回のA・B・Cと作り直したD・E以降を、単音／3回続けて聴き比べられます。採用音は記号を変えず「採用中」と表示します。候補名は生成・加工時の狙いを示し、試聴による保証ではありません。候補を切り替えると前の音を止め、停止・非表示・フォーカス喪失・離脱で連続再生の予約も取り消します。

最終選定は打撃A・最後の崩壊M・瓦礫E・走行C、途中の崩壊は音なしです。以前の候補も記録として保持します。採用済みの音を初期選択しますが、未確認の音を確認済みにはしません。[registry.ts](sound-review/registry.ts) の候補一覧へ次の記号の音源を追記すると、表示・再生・選定・プレビューへ反映されます。既存音源を変更せず、候補の記号を再利用しません。Zの次はAA以降へ続きます。音源の固定対応・ハッシュは [素材記録](../../source-assets/ouchi-barabara/audio/review/candidate-identities.json) に保持します。

「この音にする」「作り直す」「今回は音なし」「まだ選ばない」とメモを、このブラウザーに保存します。「単音で確認した」「遊びの中でも確認した」は別々に記録し、候補変更時には両方を解除します。音なしは遊びでの確認だけを記録できます。JSONを書き出して別の環境へ持ち運べます。候補の追記では既存IDの意味を変えないため、以前の選定を同じ音源の選定として読み戻せます。

固定記号への切替前に発行した2形式（`2026-11-11-v1`・`v2`）だけは、選定・メモ・追加リクエストを失わないため、既知の音源対応に従って読み替えます。ブラウザー内の旧下書きも引き継ぎ、元の保存内容は削除しません。未発行の形式を推測で読み替える処理はありません。この対応は旧下書き・JSONの移行完了後に削除できますが、時期は未定です。

途中の崩壊音の追加前に発行した4場面のJSONは、その場面だけを未選定として読み戻します。既存の選定と追加リクエストを保持するための対応で、4場面データの移行完了後に削除可能です。時期は未定です。

「追加したい音」には、場面・鳴らすタイミング・希望する音・補足を複数件記入できます。既存音の選定と一緒に下書き保存・JSON書き出し・読み戻しを行い、書きかけも保持します。追加リクエストを記入しただけではゲームに音を追加しません。

「選んだ音で遊ぶ」は別タブに試聴用のゲームを開きます。選択した候補・音なしを反映し、「作り直す」「音なし」の場面はプレビューで鳴らしません。未選定の場面は現在の音を使います。採用音のない新しい場面は、候補を選ぶまで無音です。選定情報には任意の音声URLを受け付けず、候補IDだけを使います。通常の遊びの採用音は自動変更しません。書き出したJSONの候補IDと [候補の素材記録](../../source-assets/ouchi-barabara/audio/review/README.md) を使って採用音を差し替え、ゲーム内で再確認します。

比較画面と試聴用ゲームは開発サーバー限定です。通常・AWSビルドには比較画面と新候補を含めず、公開用の一覧にも登録しません。専用検査は通常ビルド後に `node tests/ouchi-sound-review.mjs` で実行でき、対象の `test:toy` にも含まれます。

## 検証

`npm run check` と `npm run test:toy -- ouchi-barabara` を実行します。`node --import tsx tests/ouchi-model.mjs` で、全建物の全攻撃について到達可能性・歯先の一致・破壊エリアの割り当て・前進方向を検査します。あわせて、建物を建てた瞬間に画面外にあること、影が画面全体を覆うこと、画質の段階の下げ方も、縦長から横長までの画面比率で検査します。`node tests/ouchi.mjs` はヘッドレス Chromium（SwiftShader）で、3つの画面サイズでのタップ・予約上限・4回での全壊・瓦礫遊び・ループ停止を検査します。さらに、長押しの連続攻撃、次の家への移動と座標の戻し、移動後の打撃位置、キーボード操作、非表示時の停止、再入場、動きを減らす設定も検査します。効果音は実素材の取得・デコード・場面ごとの再生、同時発音上限・休止・解放、読込／音声再開の遅延・HTTP503・音声API利用不可でも操作が続くことを検査します。音色・重なった音の聴感と同期、実機iPhone/iPadでの音声開始・背景復帰、描画の滑らかさは別途確認が必要です。

ショベルカーと家は、本プロジェクトで形状を設計してコードで生成しています。外部の3D素材は含みません。ショベルカーは押し出した輪郭を部品ごとに材質単位でまとめ、描画回数を抑えています。当たり判定は車体とバケットの箱2つだけで、見た目の細かさと物理演算の負荷は無関係です。

入口カードの画像はゲーム画面のスクリーンショットです（撮影条件と変換方法は [素材の記録](../../source-assets/ouchi-barabara/README.md)）。

three.js と cannon-es（いずれも MIT）は npm から取得し、ページのスクリプトに同梱しています。ライセンス全文は `src/public/licenses/three/` と `src/public/licenses/cannon-es/` にあり、公開ビルドにも含めます。
