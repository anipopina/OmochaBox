# 開発ガイド

環境構築と基本コマンドは [全体README](../README.md)、共通の制作方針は [AGENTS.md](../AGENTS.md) を参照してください。

## 編集と検査

`src/` を編集します。Viteの開発サーバーではCSSが即時反映され、通常のTypeScriptの変更はページを再読み込みするため、遊びの状態も初期化されます。

| コマンド                                  | 内容                         |
| ----------------------------------------- | ---------------------------- |
| `pnpm run typecheck`                       | アプリとVite設定の型チェック |
| `pnpm run lint` / `pnpm run lint:fix`       | ESLintによる検査／自動修正   |
| `pnpm run format` / `pnpm run format:check` | Prettierによる整形／確認     |
| `pnpm run check`                           | 上記3種類の検査              |

Vite自体は型チェックを行いません。`pnpm run build` は型チェックを通してから `dist/` に出力します。
依存関係は `pnpm-lock.yaml` で固定し、環境構築には `pnpm install --frozen-lockfile` を使います。

VS Codeの推奨拡張はESLintとPrettierです。設定は [.vscode/](../.vscode/) にあります。原本の `source-assets/`、検証資料の `docs/`、`AGENTS.md`、生成物は一括整形の対象外です。

### Tailscaleから開発サーバーを開く

開発サーバーは `pnpm dev` で `127.0.0.1:5173` に起動し、Tailscaleの `.ts.net` ホスト名を許可します。ポート番号なしのTailscale URLがすでにローカルの5173番へ転送されていれば、そのURLを使えます。5173番を使う開発サーバーは交代で起動します。

転送が未設定の場合は、Tailscaleが動くホストで次を実行し、表示されたHTTPS URLをtailnet内の端末で開きます。

```sh
tailscale serve --bg http://127.0.0.1:5173
```

WSLで開発サーバーを動かし、Windows側でTailscaleを使う場合は、Windows側から `http://127.0.0.1:5173` に到達できることを確認します。

両方の開発サーバーを同時に使う場合は、おもちゃボックスを `pnpm dev --port 4173` などで別ポートに起動し、Tailscale Serveにも別のHTTPSポートを割り当てます。

## 新しい遊びの開発とレビュー

1. 最新の `main` から作品ごとのブランチ `feat/<slug>` を作ります。本体・素材・一覧のカード・詳細検査を同じブランチで揃えます。途中で差分を共有するときはDraft PRを使えます。[ページと素材の追加](#ページと素材の追加)
2. 作品ブランチで `pnpm run check` と `pnpm run test:toy <slug>` を実行します。レビュー担当が遊べる状態になったら、必要に応じてSitesへ検証版を公開します。検証範囲は [検証範囲の選び方](#検証範囲の選び方) に従います。
3. 独立した実画面レビューを行い、確認した作品のコミット・結果・未確認事項をPRに残します。Sitesを使った場合はURLと版番号も記録します。`main` の更新を取り込んだ後に作品や依存する共通部分が変わった場合は、影響する操作を再確認します。
4. ユーザーが確認した作品から、作品ブランチのPRを個別に `main` へ取り込みます。試行錯誤のコミットはSquash mergeでまとめられます。本番で通常表示するかは別途ユーザーが決めます。[AWS本番公開](../infra/README.md)

この手順は新作をレビューしながら進めるときの標準です。メンテナーは必要に応じて `main` へ直接pushできます。

### Sitesで複数の候補を確認する

既存のSitesプロジェクトでは、検証URLにその時点でデプロイしているビルドが表示されます。レビューが続いている候補を同時に遊べるよう、Sitesを更新するたびに次の手順でまとめます。[Sitesプロジェクト設定](../.openai/hosting.json)

1. 最新の `main` からローカルに一時ブランチを作り、その回に確認する作品のコミットをマージします。作業中の変更がある場合は `git worktree` で別の作業ツリーを使えます。前の版から引き続き確認したい作品も含めます。例えばAを更新してBのレビューが続いている場合は、Aの新版とBの確認中のコミットを入れます。Aが `main` に入った後は、最新の `main` とBの候補で組み立てます。
2. 一覧やテスト対応表で追記が競合した場合は、候補すべての登録を残します。作品自体の修正は作品ブランチに反映し、検証用にも取り込みます。
3. 一時ブランチから `pnpm run build` で全作品入りの `dist/` を作り、ビルドと同じソースで既存Sitesプロジェクトへ公開します。公開された版番号と、そこに含めた作品のコミットを、対応するPRに記録します。
4. 公開版を確認し、版とコミットを記録したら一時ブランチを削除します。専用の作業ツリーを使った場合はそれも片付けます。一時ブランチはローカルで管理し、修正と `main` への取り込みは各作品ブランチから行います。

## ページと素材の追加

- `src/<slug>/` に `index.html`・`app.ts`・`style.css`・`README.md` と必要な素材を置きます。`index.html` に `<script type="module" src="app.ts"></script>` を記載します。ViteがHTMLを自動検出し、`/<slug>/` で開けます。
- 一覧への登録は [src/games.json](../src/games.json) で管理します。本番公開の選択は [config/production-games.json](../config/production-games.json)、AWSの手順は [infra/README.md](../infra/README.md) を参照してください。
- 各遊びにREADMEを用意し、遊び方・状態の扱い・実装上の注意・素材の出典へのリンク・固有の確認項目を記載します。
- `../` への戻るリンク、終了・非表示時の音声と入力の後始末、共有画像・faviconを備えます。anipopina.comへのリンクは入口ページのフッターに置き、遊び個別のページには不要です。操作寸法などは [AGENTS.md](../AGENTS.md) に従います。
- `app.ts` で [共通のメディア設定](../src/shared/play-media.ts) を読み込み、Canvasや画像を長押ししたときの選択・保存メニューや画像の標準ドラッグを抑えます。
- 画像・音声は `import imageUrl from './assets/image.webp'` のように参照し、`image.src = imageUrl` や `fetch(audioUrl)` に渡します。CSSの `url()` とHTMLの画像参照もViteが処理し、公開用にはハッシュ付きファイル名を付けます。
- 固定URLが必要な素材は `src/public/` に置き、`/favicon.ico` のように参照します。ビルド時に `dist/` 直下へコピーされます。
- 共有キャラクターSVGは出典・SHA-256とMatter.jsの当たり判定を登録します。配置、利用例、ローカル確認画面は[キャラクターSVGの追加手順](../src/assets/characters/README.md#svgを追加するとき)を参照してください。
- 素材原本と出典・利用条件・変換記録は `source-assets/<slug>/` に保存します。生成効果音の原本WAVはGit管理外の `tmp/audio-originals/<slug>/` に保管し、比較・配信用MP3と制作記録だけをリポジトリに保持します。確認すべき利用条件は [AGENTS.md](../AGENTS.md) を参照してください。`dist/` を直接編集しません。

### 入口カード画像の作り方

- **遊びの中で起きることを一枚で伝える。** 一覧の小さな表示でも遊びが伝わるよう、主役や動きがわかる効果を大きく見せます。何が起きているか読み取れれば、画像の端で一部が見切れても構いません。
- **実際の遊びの素材を優先する。** ゲーム画面の撮影や、使用中のキャラクター・背景・エフェクトの再構成から始め、カードに合わせて配置や明暗を調整します。
- **背景と効果を含めて一枚に書き出す。** 1200×600（2:1）のWebPを目安に `src/assets/previews/` へ置き、`src/previews/<slug>.ts` から参照します。
- **トップページで確認する。** スマートフォン幅と広い画面で、隣のカードと表示サイズが揃い、切り抜き後も主役や効果が読み取れるかを確認します。

## ブラウザーテスト

既存のChromium / DevTools Protocolのテストを使います。Linuxでの既定の実行ファイルは `/usr/bin/chromium` です。異なる場合は絶対パスを指定します。

```sh
CHROME_PATH=/path/to/chromium pnpm test
```

### 検証範囲の選び方

| 変更・目的 | 実施する検証 |
| --- | --- |
| 効果音の比較候補・台帳・制作記録だけの反復 | `pnpm run sound-review:check <slug>` と対象候補の試聴。ビルド・ゲーム詳細テストは省略。[効果音の制作・選定](sound-review.md) を参照 |
| 比較ツールのコード変更／音の最終採用 | [効果音の制作・選定の検証表](sound-review.md#反復中と採用時の検証) に従う。ゲーム側の再生処理を変える場合は選定途中でも対象の詳細検査を行う |
| 毎日の遊び追加・個別修正 | `pnpm run check` と `pnpm run test:toy <slug>`。対象の独立した実画面レビューも行う |
| テスト運用スクリプトだけの変更 | `pnpm run check`、`pnpm run test:runner` と変更に対応する代表テスト。全体回帰の反復は不要 |
| 入口の一覧・遷移 | `pnpm run check` と `pnpm run test:smoke` |
| 共通の戻るボタン | `pnpm run check`、`pnpm run build`、`pnpm run test:home-button`（全作品・3画面サイズ） |
| その他の共通処理 | 依存する遊びを `pnpm run test:toy <slug1> <slug2>` で指定し、変更内容に応じた確認を追加 |
| 広範囲の依存・Vite・共通基盤、影響不明、横断的な問題、AWS本番へのまとめ反映前 | `pnpm run check` と `pnpm run test:full` |

`pnpm test` は `test:smoke` の別名です。日常の追加に無関係な作品の詳細回帰・AWS用ビルドは必須にしません。Sitesは全作品を公開する検証環境です。無関係な既知の失敗は新作の公開ゲートにせず、対象・理由・未確認事項を報告します。対象の失敗や真の共通回帰は解消または明示し、未確認を成功扱いにしません。定期実行は設定していません。

### 実行コマンドと対象対応表

```sh
pnpm run test:list
pnpm run test:toy pitatto-magnet
pnpm run test:smoke pitatto-magnet
pnpm run test:full
pnpm run test:runner
```

`test:toy` は通常ビルド・出力素材検査、対象の入口から開く・戻る・再入場・初期素材読み込み、対象のモデル／ブラウザー詳細検査を実行します。`test:smoke` は通常ビルド・出力素材検査と軽い往復確認だけで、省略時は全作品、slug指定時は対象作品を確認します。共通確認は1画面サイズで実行し、各作品の詳細操作や音の聴感を保証するものではありません。変更した操作で後から読む素材は詳細検査と実画面レビューで確認します。

対応表の正本は [tests/test-plan.mjs](../tests/test-plan.mjs) で、`test:list` から表示できます。新作は [src/games.json](../src/games.json) と対応表の両方に登録します。未登録・誤記・不要な引数はエラーになります。既存の `browser.mjs` はおえかきと窓、`toy-interactions.mjs` はいろガラスとみずたまりを含むため、これらの組合せは一緒に検証します。`stamp.mjs` に残るおえかきの設定非依存確認も維持しています。おえかき・窓の詳細検査にはテスト用ビルドも作ります。各単体スクリプトは従来どおり直接実行できますが、必要なビルドを先に用意してください。

`test:full` は通常・AWS・テスト用ビルド、公開範囲・インフラ・素材、全作品の詳細検査を実行します。各検査の失敗後も独立した検査を続け、結果と秒数を一覧表示します。前提ビルドが失敗した検査は古い出力で実行せず `SKIP` にします。`FAIL` または `SKIP` があれば終了コードは非ゼロです。集約結果は `test-results/<toy|smoke|full>-summary.json`、既存の結果・スクリーンショットも `test-results/` に保存します。同じ作業場所で複数の実行を重ねないでください。運用スクリプト自体は `test:runner` の小さな検査で、選択範囲・引数検証・失敗継続・依存スキップを確認できます。

専用一時プロファイルと自動選択ポートを使い、終了時にブラウザーとHTTPサーバーを停止します。ヘッドレス検証では `--no-sandbox` を指定するため、対象はこのローカルコードだけにしてください。エミュレーションとは別に、実機iPhone/iPadのSafari、OSジェスチャー、音の聴感も確認します。

見た目・操作を変更した場合は、通常時と「動きを減らす」設定時の操作結果、およびページ終了・非表示・復帰時の入力・音声・描画の後始末を、変更に応じて確認します。検証結果の報告方法は [AGENTS.md](../AGENTS.md) に従います。

### テスト用ビルド

公開用の `dist/` では、入口・各ゲームの基本操作と素材参照を検証します。内部状態を確認する詳細な回帰テストには、`pnpm run build:test` で作る `test-results/build/` を使います。

テストモードに限り、[Vite設定](../vite.config.ts) が [hikari-hook.js](../tests/fixtures/hikari-hook.js) を描画ゲームのクロージャー内へ挿入してからコンパイルします。挿入箇所が変わるとビルドを失敗させます。公開用への混入は出力検査で検出します。`test-results/` は公開対象に含めません。

## 音と振動

音・振動を採用する遊びでは、操作に応じた反応として使います。遊びの音量設定UI・音量設定のブラウザストレージへの保存は設けず、音量・消音は端末やブラウザで調整します。ページを開いたときや復帰しただけでは鳴らしません。音が使えなくても遊べるよう、操作結果は形や動きでも伝えます。

### 効果音の制作と素材管理

効果音は遊びごとに順次追加します。鳴らす操作・出来事、音の印象、長さ、繰り返し方を先に決め、Stable Audioなどで生成した候補を試聴して選びます。幼児が驚く大音量、鋭すぎる音、意図しない声・音楽・ノイズを避けます。既存の合成音も用途に合えば維持し、生成音への一律の置換やBGMの追加は行いません。

比較画面・ゲーム内プレビュー・固定記号での候補追加・JSONでのフィードバックと検証の分け方は [効果音の制作・選定](sound-review.md) を正本とします。候補の再作成中は軽い検査で反復し、最終採用時に対象ゲームを検査します。

生成原本WAVはGit管理外の `tmp/audio-originals/<slug>/`、制作記録は `source-assets/<slug>/audio/`、比較用MP3は `src/<slug>/sound-review/assets/`、採用ファイルは `src/<slug>/assets/` に置きます。記録には次を残し、生成用の仮想環境・モデル重み・キャッシュ・認証情報は同梱しません。

- 生成元、モデル名と版、生成日、プロンプトと除外指示、seed・生成条件、使用ツールの版など、候補を追跡できる情報。seedだけで同じ結果を保証しません。
- 採用原本と配信用ファイルの対応、切り出し・フェード・音量調整・圧縮の条件、配信形式・長さ・容量とファイルのハッシュ。
- 使用したモデル・サービスの利用条件の参照先と確認日、生成音の改変・公開リポジトリへの同梱・Web配信・商用利用の可否、必要な帰属表示やLICENSE・NOTICE。モデル自体の配布条件と生成音の利用条件を区別し、無料提供やログイン時の同意だけで利用可能と判断しません。不明点は採用前に解消します。

不要な無音を除いて操作とのずれを減らし、必要な余韻は残します。切り出し端のクリック音や音割れを避け、他の効果音との聴感上の音量を合わせます。各ファイルをピーク値だけで一律に最大化しません。配信は対象ブラウザーで再生できる圧縮形式を選び、容量とデコード後のメモリーも抑えます。加工・圧縮後の音を再度試聴します。

### 組込みと確認

- Web Audioの開始・再開はユーザー操作を起点とします。読込・デコードは使い回し、操作ごとに取得や音声コンテキストを増やしません。音の準備ができなくても視覚的な反応を待たせず、読込・再開の完了後に古い操作の音を遅れて鳴らしません。
- 連打・長押し・複数指・自動連鎖でも音が積み上がらないよう、発音間隔・同時発音数・全体の音量を制限します。具体的な上限は各遊びの実装で定義します。
- 音声ノード・再生予約・非同期処理の所有者を明確にし、キャンセルや終了に応じて停止・解放します。非表示・フォーカス喪失・離脱で停止し、遅れて完了した処理も再生させません。復帰後は次の操作まで鳴らしません。
- 各遊びのREADMEと素材記録を実装に合わせて更新し、「無音」「合成音」「音声ファイルなし」などの説明を見直します。過去の検証記録は現在の仕様に書き換えません。

検証範囲は [検証範囲の選び方](#検証範囲の選び方) に従います。対象の詳細検査では、初回操作・連打・複数指・読込遅延／失敗・音声API利用不可・キャンセル・非表示／復帰・再入場を変更に応じて確認します。配信素材の取得・デコードと再生上限を確認し、音を追加しても入力や視覚的な反応が損なわれないことを確認します。

人による試聴では、単音と重なった音の音量・音色・操作との同期・消え際を確認します。実画面の表示・操作確認とは別に記録します。機械的なピーク検査やヘッドレスの音声API検査を聴感確認の代わりにはしません。ブラウザーでの確認と実機iPhone/iPadのSafariでの音声開始・背景復帰・聴感確認を区別し、未試聴・実機未確認は報告に残します。

スタンプの粒子・音・触覚の上限と対応状況は [スタンプREADME](../src/ponpon-stamp/README.md#配置フィードバック) を参照してください。
